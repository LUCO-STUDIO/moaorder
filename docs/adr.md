# 모아오더 ADR (Architecture Decision Records)

모든 결정의 기저 원칙: **빠른 출시 > 멋진 구조. 현장 운영 혼선 감소가 핵심 가치.**

---

## ADR-001: 프론트엔드 — SvelteKit (SSR + CSR 혼합)

**결정:** SvelteKit. 공구 상세 등 공개 페이지는 SSR, 나머지는 CSR 혼합.
**이유:** 카카오 링크 공유 시 OG 태그가 서버에서 렌더돼야 미리보기 작동. 2인 팀에서 빠른 개발과 경량 구조가 필요.
**대안 기각:** Next.js 단일 풀스택 — 1인이면 유리하지만 2인 역할 분담(프론트/백 분리)에는 SvelteKit + FastAPI가 적합.

## ADR-002: 백엔드 — FastAPI + SQLAlchemy 2.0

**결정:** FastAPI (async) + SQLAlchemy 2.0 + Alembic.
**이유:** 공동창업자 백엔드 10년 경력. 구현 속도 + 타입 힌트 + async 지원. Pydantic을 입력 검증 단일 진실원천으로 사용.
**대안 기각:** Django — ORM은 좋지만 async 지원 약하고 FastAPI 대비 보일러플레이트 많음.

## ADR-003: 공구 1개 = 상품 1개

**결정:** MVP에서 공구와 상품을 1:1로 고정. groups 테이블에 상품 정보 포함.
**이유:** 여러 상품 → 장바구니형 주문 → 부분취소/집계/환불 복잡도 급증. 여러 상품 필요 시 공구 여러 개 생성으로 해결.
**향후:** 묶음 공구는 검증 후 별도 설계.

## ADR-004: 3가지 공구 타입 전부 MVP 지원

**결정:** 예약주문형/공동구매형/픽업형 모두 지원.
**이유:** 파일럿 사장님이 세 가지를 모두 실제로 운영 중. 하나만 지원하면 서비스 전환 불가.
**구현 방식:** 공통 주문 흐름 + 타입별 규칙 분기 (별도 플로우 3벌 아님).

## ADR-005: 주문 상태와 환불 상태 분리

**결정:** orders에 refund_status 없음. 환불은 order_adjustments 테이블에서 관리.
**이유:** 취소는 주문 생애주기, 환불은 금전 처리. 성격이 달라서 하나의 상태열에 넣으면 API/UI가 꼬임. 부분취소 이력 추적도 필요.

## ADR-006: CONFIRMED와 PREPARING 통합

**결정:** 마감 시 PAID → CONFIRMED 전이만. PREPARING 상태 제거.
**이유:** 현장에서 사장님이 "준비 시작" 버튼을 별도로 누를 가능성 낮음. 마감 후 자동으로 피킹 리스트가 준비되는 게 더 자연스러움.
**고객 라벨:** "주문 확정" + 서브텍스트 "상품 준비 중이에요"로 이해도 보완.

## ADR-007: 재고 선점 → 결제 → 웹훅 확정

**결정:** 결제 전 재고 선점(inventory_holds), 웹훅으로만 주문 확정. 프론트 리다이렉트 불신뢰.
**이유:** 결제 후 재고 없음 케이스 원천 차단. 결제 성공했는데 주문 안 되는 최악의 UX 방지.
**TTL:** 10분. 만료 시 워커가 remaining_qty 복원.
**동시성:** PostgreSQL 조건부 UPDATE (`WHERE remaining_qty >= n`). 별도 락 불필요.

## ADR-008: API와 Worker 분리

**결정:** 같은 코드베이스, 별도 프로세스. Railway에서 2개 서비스로 배포.
**이유:** FastAPI 인스턴스 다중 실행 시 APScheduler 중복 위험. 재배포 시 스케줄러 불안정. API와 워커는 수명주기가 다름.
**대안 기각:** Celery + Redis — MVP에서 인프라 오버헤드. DB 폴링으로 충분.

## ADR-009: 알림 — DB 폴링 단일 테이블

**결정:** notifications 테이블이 발송 큐 + 사용자 알림 목록 겸용. 워커가 1분 간격 폴링.
**이유:** 서버 재시작해도 누락 없음. 디버깅 용이 (DB에서 바로 확인). 모든 알림(인앱/SMS/이메일)을 한 곳에서 관리.
**대안 기각:** APScheduler 인메모리 — 재시작 시 유실. pg_cron — 채널 추가 시 관리 어려움.

## ADR-010: 단일 JWT 7일

**결정:** Access + Refresh 분리 안 함. 단일 JWT 7일, httpOnly 쿠키.
**이유:** 2인 팀이 refresh 로직까지 구현하는 건 속도 대비 과도. httpOnly 쿠키로 XSS 방지.
**조건:** 같은 루트 도메인 (moaorder.com + api.moaorder.com). sameSite=lax.
**향후:** 보안 강화 필요 시 토큰 분리.

## ADR-011: 실시간 업데이트 — 10초 폴링

**결정:** SSE/WebSocket 대신 10초 간격 폴링.
**이유:** MVP 규모에서 SSE/WebSocket은 인프라 복잡도 대비 가치 낮음. 사장님 대시보드는 10초 지연 허용 가능.
**향후:** 사용자 수 증가 시 SSE 검토.

## ADR-012: Presigned URL 이미지 업로드

**결정:** 클라이언트 → R2 직접 업로드. FastAPI는 Presigned URL만 생성.
**이유:** 서버 부하 없음. 대용량 이미지 문제없음. Cloudflare R2 10GB 무료.

## ADR-013: 비즈니스 모델 — 구독 수수료

**결정:** MVP는 사장님 월정액 구독. 거래 수수료 모델은 후순위.
**이유:** 거래 수수료 → 플랫폼 정산 구조 필요 → 복잡도 배 증가. 월정액은 PG 연동이 단순(고객 → 사장님 직접 결제).

## ADR-014: User:Store = 1:N 스키마, 1:1 정책

**결정:** DB는 멀티매장 구조, MVP 운영은 사장님당 매장 1개.
**이유:** 1:1 → 1:N 마이그레이션 비용이 초기 일반화 비용보다 훨씬 큼. 지점 추가만으로 스키마 변경 불필요.

## ADR-015: 공유 URL — public_id (nanoid 12자리)

**결정:** groups.public_id를 공유 URL에 사용. 내부 API는 UUID.
**이유:** UUID 직접 노출보다 짧고 안전. 카카오 링크에 적합.
**형식:** `moaorder.com/g/{public_id}`

## ADR-016: Vercel + Railway 배포

**결정:** SvelteKit → Vercel(서울), FastAPI/Worker/PostgreSQL → Railway(도쿄).
**이유:** 초기 비용 월 $5~10. 빠른 배포. Vercel은 SvelteKit SSR에 최적.
**조건:** 같은 리전 배치 (Vercel 서울 + Railway 도쿄, 가장 가까운 옵션).

## ADR-017: 자동 매장 구독 (첫 주문 시)

**결정:** 고객 온보딩에서 매장 선택 제거. 첫 주문 완료 시 자동 구독.
**이유:** 매장 탐색 기능 없이 매장 선택 단계를 두면 빈 화면. 카카오 링크 유입 → 주문 → 자동 구독이 가장 자연스러운 전환.

## ADR-018: 초안 상태 제거

**결정:** 공구 생성 = 즉시 게시. 초안(draft) 상태 없음.
**이유:** 임시저장을 MVP에서 뺐으므로 초안 상태가 시스템 내부에서만 의미. 상태 1개 줄이면 프론트/백 분기와 QA 포인트도 줄어듦.

## ADR-019: 수령 완료 — optional 체크 + 공구 전체 완료

**결정:** 고객별 수령 체크는 선택, 공구 전체 완료가 주 액션.
**이유:** 바쁜 사장님이 고객마다 폰 들고 체크하기 비현실적. 전체 완료 시 미체크 주문은 NOT_PICKED_UP으로 분리해 후속 처리 가능.

## ADR-020: 수량 늘리기 불가, 줄이기만

**결정:** 마감 전 수량 줄이기(부분환불)만 지원. 늘리기는 새 주문 유도.
**이유:** 늘리기 → 추가 결제 건 → 정산 분산 + 주문 묶음 로직 필요 → MVP 복잡도 폭증. 줄이기는 원결제건 부분취소로 깔끔.

## ADR-021: Idempotency 전략

**결정:** 핵심 API에 idempotency key. 테이블에 resource_type별 TTL 차등.
**이유:** 주문 생성(웹훅), 환불, 자동 마감, 알림 발송은 중복 실행 시 치명적. payment_id, dedupe_key 등 자연 키 활용.

## ADR-022: 에러 응답 + request_id

**결정:** 통일된 에러 JSON + 모든 요청에 request_id 부여.
**이유:** 프론트는 error.code로 분기, message는 사용자에게 직접 표시. request_id로 로그 추적.

## ADR-023: 픽업형 — 레벨 1만 (슬롯 선택, 인원 제한 없음)

**결정:** 픽업 시간대 선택 + 30분 전 리마인더. 슬롯별 인원 제한은 후순위.
**이유:** 파일럿 규모에서 슬롯 정원 관리 불필요. 공구 재고 + 슬롯 재고 동시 관리는 복잡도 높음.

## ADR-024: 알림 채널 — 인앱 + 이메일 우선, SMS 후순위

**결정:** MVP 1차는 인앱 + 이메일. SMS는 사업자 준비 후.
**이유:** SMS는 발신번호 등록 + 사업자 인증 필요. 이메일(Resend/SendGrid)은 즉시 연동 가능.
**카카오 알림톡:** 2차 (심사/승인 리드타임).
